# The lessdumb learning model

The MVP contains 710 original skills, 2,840 questions, 648 executable exercises, and 1,420 cards across Python, quantitative foundations, data analysis, machine learning, data systems, competitive programming, Rust, and C++. The learning engine operates on a subject-neutral graph. A course is a selection of skill IDs; each skill names its domain, unit, course, and prerequisites. Additional programming languages, mathematics, physics, and natural languages can use the same registry and scheduler. Learning functions accept an optional `CurriculumCatalog` so another catalog can be evaluated independently of the public curriculum registry.

## Sources and boundaries

The user-supplied _The Math Academy Way_ PDF informed the learning design. Relevant sections describe prerequisite graphs (printed pages 69–75), mastery and the knowledge frontier (207–214), spaced repetition (251–264), mixed practice (271–280), and retrieval practice (285 onward). Those are design principles, not executable instructions. lessdumb uses an independently written curriculum and a transparent scheduler built on FSRS-6; it does not claim to reproduce Math Academy's proprietary model or its research outcomes.

The supplied local reference datasets were inspected for structural patterns only: courses/categories, graph nodes and edges, topic groups, problem difficulty, and quiz metadata. Their proprietary lessons, questions, answer data, assets, and extraction/exploit scripts are not imported into this application.

Python behavior was checked against the official documentation: [numbers, strings and lists](https://docs.python.org/3/tutorial/introduction.html), [control flow and functions](https://docs.python.org/3/tutorial/controlflow.html), [data structures](https://docs.python.org/3/tutorial/datastructures.html), and [errors and exceptions](https://docs.python.org/3/tutorial/errors.html). Assertions grade observable results for finite authored inputs; they do not prove use of a required API, asymptotic complexity, or generalization to every input. Every reference code solution is executed against its assertions in the test suite, and each displayed example is executed to verify its documented output.

## Evidence before progression

Skills are being converted to [knowledge points](knowledge-points.md). A skill with knowledge points is mastered when one lesson attempt passes every point (two correct answers on different questions each) and, where its policy requires code, the skill's code exercise. Points passed during an attempt stay provisional and become evidence together when the attempt completes; three incorrect answers on one point fail the attempt and discard its progress. A skill without knowledge points is still mastered only when all four distinct questions have been answered correctly and independently: three test recognition or prediction, and the fourth requires running its declared language successfully against assertions. Repeating one correct choice cannot unlock a skill in either form. The numeric mastery display is the fraction of distinct lesson evidence; prerequisite checks recompute from the evidence IDs instead of trusting a stored score.

Assessment policies belong to skills rather than being universal Python assumptions. Every supplied question requires independent successful evidence for mastery. A skill can declare the question types required within a review cycle and its number of review answers. Python, Rust, and C++ explicitly require code and choice evidence in a two-answer cycle. Without an explicit policy, the engine uses the skill's available question types and up to two review answers. Knowledge-point questions meet a choice requirement; for those skills `reviewAnswers` counts the points reviewed, one fresh variant each, and the code exercise is asked in addition. Choice-only math or vocabulary skills can therefore be mastered and reviewed without an executable exercise or Python runtime. Future formats can extend the question union when needed.

New lessons are selected from the knowledge frontier: skills whose full prerequisite ancestry has mastery evidence. Questions not previously attempted are served before retrying a missed question. After a failed knowledge-point attempt the scheduler offers other available work first; the lesson returns after the learner completes another task or four hours later, whichever comes first, and restarts at its first point. A learner can inspect the graph, but learning submissions for locked skills are rejected. Viewing a lesson earns no XP.

The lesson page follows the scaffolded sequence described in Math Academy's public learning process and the supplied PDF (pages 74–75, 219, and 397): a plain page with the lesson title and one progress marker per knowledge point (plus the code step), the current point's explanation and worked example, then one question at a time with lettered choices, Submit, immediate feedback showing the explanation, and Continue. Skills without knowledge points keep their introduction and worked-example slides before practice. Choices are shown in a deterministic shuffled order per presentation and graded against the authored answer index. Each graph skill remains an independently assessed atom; a topic's four stages retain their own graph identities. There are no hints: the worked example is the support. Reviews show no lesson material. Older saved answers flagged as assisted are still read and still never count as evidence.

A wrong answer removes evidence only for that question. Descendants are unavailable until the missing evidence is restored. Other prerequisite evidence is preserved: a mistake in a difficult skill is not proof that every ancestor is weak. If an ancestor separately loses its own evidence, the frontier naturally selects that ancestor first. This is targeted remediation based on observed evidence.

## Retrieval and spacing

Initial mastery schedules the first review one day later. A code-bearing review cycle requires two distinct unassisted correct answers, including an executable code question; other subjects follow their declared assessment policy. Only a due review can strengthen the schedule. Completed independent cycles use the maintained `ts-fsrs` implementation of FSRS-6 to update that learner/skill’s stability, difficulty, lapse count, and review date. The target retention is 90%, with deterministic scheduling and a 365-day maximum. A completed cycle containing an answer flagged as assisted (only older clients produced these) is graded Hard; otherwise it is Good. Assisted answers alone never complete a cycle or move its due date. A failure records Again, lowers memory strength, and clears the failed question’s evidence. Repair keeps that reduced memory state and sets a conservative one-day check. Default FSRS weights are shared; parameters are not trained per learner. Early practice does not move the due date or earn review XP. A failed question restores the skill to learning/remediation and starts a one-day review interval after its evidence is repaired.

Due reviews come before new learning, but never more than two in a row while a lesson is ready (`MAX_CONSECUTIVE_REVIEWS`): after two finished review tasks since the learner's last lesson answer, the next task is a lesson, and then reviews resume. A review task is finished when its cycle passes or a missed answer ends it. When no lesson is ready, reviews simply continue, and `/learn?mode=review` stays a review-only session. The Learn task list follows the same rule. When several skills are due, adaptive sessions interleave after each answer so the last practiced skill is not repeatedly selected. Directly opening a specific skill keeps a focused session. Within the course-priority group, due candidates with lower estimated recall come first. A due descendant whose prerequisite needs remediation waits until that prerequisite is restored. The scheduler makes no claim that success in an advanced skill demonstrates retention of every ancestor; implicit credit (below) reaches direct prerequisites only.

## Implicit review credit

Every prerequisite edge means the dependent skill's lesson or questions actually use that skill ([graph rules](knowledge-graph.md)), so succeeding at a skill also exercises its direct prerequisites, in the spirit of Math Academy's FIRe. Each skill encompasses its direct prerequisites with a weight in (0, 1]: `encompasses` on the skill when authored, otherwise every direct prerequisite at 0.25 (`DEFAULT_ENCOMPASS_WEIGHT`). The weights are authored heuristics, not parameters fitted to learners, and the default is deliberately low.

When a learner completes a lesson or a review cycle of a skill, or answers it correctly in a quiz, each encompassed prerequisite that is mastered, unlocked, scheduled, and not part-way through its own review cycle gets implicit credit. Its due date moves later by the weight times the interval a full successful review at that moment would add (FSRS Good from its current memory), so it can never move past what a real review would schedule. Credit is given at most once per prerequisite per calendar day, and never on the day the prerequisite was itself learned or reviewed, so a new skill keeps its first one-day check. Credit stops at direct prerequisites; nothing trickles further up the graph. It changes only the due date: FSRS stability, difficulty, repetitions, and estimated recall change only through real reviews, so a later real review sees the full elapsed time. Failures give no credit and change nothing upstream. A lapsed or remediating skill is not mastered and gets nothing, and credit never creates mastery. A quiz miss, a real review, or a lapse after a credit takes precedence over it.

The credit is recorded on the prerequisite (`implicitCredit`: source skill, weight, time, and the due date before and after) and on the answer that gave it (`credited`), so merges keep a credit that a stale device lacks, and the history feed can note "+ reviewed N prerequisites". The graph's detail panel lists which skills also review a skill and notes when practice moved its next review.

Review compression: among due reviews, after course priority and the rule that keeps the most recently practiced skill from repeating, the scheduler prefers a review whose success would credit more skills that are due or due within a day. The interleaving with lessons is unchanged.

## Quizzes

After about 150 XP of lessons and reviews since the previous quiz (`QUIZ_XP_INTERVAL`, quiz XP excluded), a quiz appears on Learn as a task card ("Quiz N" with its XP). It asks 8–12 multiple-choice questions, normally ten, one from each of up to ten skills the learner has mastered on the active course path, supporting skills from other courses included. Skills not quizzed recently come first, then the active course, then the most recently practiced. Each question is a variant of the skill's least-practiced knowledge point that the learner has seen least, unseen first; when fewer than eight skills qualify, skills contribute a second question from another point, and with fewer than four no quiz is offered. The time limit is 90 seconds per question and is shown as a countdown. During the quiz there is no lesson material, no feedback, and no explanation; at the end the learner sees the score, the XP, and every question's result with its explanation. Unanswered questions at the time limit count as missed.

A missed question makes its skill's review due immediately and starts a fresh review cycle; it does not remove lesson evidence or record an FSRS lapse by itself, so the remedial review decides, and failing it records Again as any review does. A correct quiz answer on a skill whose review is already due counts toward that cycle, but only a review answer can complete a cycle, so a quiz never moves a due date forward. A correct answer on any other skill changes no schedule, just as early practice does. These are deliberately conservative choices: FSRS memory changes only through review tasks. Quiz difficulty is not adapted toward a target score; doing that honestly would need calibrated per-question difficulty, which the catalog does not have.

## Progress, XP, and cards

Progress updates are immutable and have an explicit schema version. Version 4 adds implicit review credit; version 3 adds saved quizzes (the latest 50, each with its questions, answers, score, and XP) and quiz answers in the attempt log; version 2 adds the lesson attempt in progress, the last failed attempt time, and a one-time lesson reward flag per skill; version 1 accounts migrate when they are read, and mastery earned under the four-question lesson is kept when a skill gains knowledge points. Only the latest 2,000 events are retained for diagnostics, while durable per-question evidence checkpoints, permanent reward IDs, per-skill XP/calendar totals, and answer counters survive compaction. Per-runtime writer counters merge by component maxima, so a late offline observation is counted even when its timestamp predates another device’s newest work. Writer contributions are retained rather than silently evicted. Merges reconcile different evidence from the same review cycle once, preserve newer retention events across newer lesson reads, and do not resurrect a compacted failure from a stale device. Simultaneous conflicting retention outcomes choose a deterministic conservative memory state, so device merge order does not decide the review date. Stable attempt IDs deduplicate retries within the retained event window. Attempt history records question ID, skill ID, answer outcome, the legacy assisted flag, practice mode, timestamp, awarded XP, and, on the answer that completed or failed a task, its task outcome. Epoch milliseconds represent scheduling times; ISO strings represent attempt timestamps and the first mastery timestamp. Calendar dates and streaks use the learner's recorded IANA timezone.

XP is paid per completed task (`src/lib/xp.ts`), on the answer that completes it, at about one XP per focused minute: a lesson is worth three XP per knowledge point plus two (or its estimated minutes for a skill without knowledge points), with a quarter bonus for a perfect task and one XP less per incorrect answer, never below one. A lesson pays once per skill: a one-time reward flag, plus the older per-question reward ledger netted against the award, prevents relearning, remediation, or deliberate failure from farming it. Failed attempts earn nothing. A quiz is worth 1.5 XP per question, rounded (15 XP for ten questions), scaled by accuracy and rounded: nine of ten correct earns 14 of 15 XP. Quiz XP is recorded on the quiz itself, so merges count each quiz once. A due review cycle earns its review XP once; merges credit a lesson or cycle completed on two devices once. XP measures completed practice in this application; it does not certify programming proficiency.

Flashcards contain one idea each and are associated with stable skill/card IDs. Mastered skills earn their two cards for automated Anki export/sync. The full registry remains available for explicit curriculum previews. Each card is original, and deterministic IDs let the integration update existing notes instead of creating duplicates.

## Verification and limitations

Tests cover graph references and cycles, mastery evidence, knowledge-point passing and failure, retry cooldown, shuffled-choice grading, legacy assisted answers, schema migration, prerequisite gates, question rotation, review timing, distinct executable review evidence, XP replay resistance, immutable updates, timezone/streak boundaries, and reachability of each course and its full prerequisite path. Real Pyodide executes all 266 solutions and 273 executable lesson examples with the locally served scientific packages. The original Python course also retains native execution and choice-output verification. Native Rust and C++ batches verify all 308 new solutions and 308 runnable examples, and reject each unfinished starter and empty submission. Real browser runs separately verify Compiler Explorer grading, account persistence, automatic cards, prerequisite unlocks, and a due code-plus-choice FSRS review in each language. Provider outages preserve evidence. Python stays in a browser worker; compiled source is transmitted without account data through the documented sandbox adapter. See [runtime boundaries](compiled-code.md). Test-only math and vocabulary catalogs verify cross-course prerequisites, choice-only mastery/review, and a custom one-answer review policy. The production catalog includes original cross-course math, data, ML, systems, and contest nodes. Competitive Programming reuses the real Python function path and connects geometry to quantitative vectors; it has no separate or implicit unlock store.

FSRS supplies a published memory model and per-item adaptation, but these estimates have not been validated or individually fitted on lessdumb learners. The one-day acquisition/repair check is a conservative product rule. Legacy schedules migrate on the next memory event without moving existing due dates. Authored questions (four per legacy skill, three or more per knowledge point) provide finite evidence rather than unlimited randomized assessment. The MVP has no credit transfer beyond implicit review credit along direct prerequisite edges, and no placement test. The generic graph and versioned progress contract leave room for those features without replacing the learning record.

## Atomic contest topics

Competitive Programming has 48 original application skills plus 144 prerequisite concepts. Each topic’s four skills have stable topic/stage metadata, a short lesson, runnable example, three conceptual checks, one executable assessment, and two recall cards. Prerequisites, not stage numbers, govern eligibility: a concept that does not use its sibling is available alongside it, and the application requires every concept it uses. Topic application IDs and existing evidence remain valid; the new prerequisites still need independent evidence. Graph rows display the four skills together, with real cross-topic and cross-course edges. The focused view omits unrelated lines and edges implied by other prerequisites; Show all connections restores every declared graph edge. The detail panel lists the whole topic and explains saved evidence on mastered-but-locked nodes. Display filtering never changes eligibility.

## Atomic language courses

Rust has 32 four-skill topics (128 skills); C++ has 45 (180 skills). Stage metadata uses the same graph presentation and evidence model as competitive programming. Both begin independently at their own first program. Each course keeps one explicit prerequisite map (`src/lib/courses/rust/prerequisites.ts`, `src/lib/courses/cpp/prerequisites.ts`) in which every edge names a construct the skill actually uses, so ownership, lifetimes, abstractions, concurrency, and systems applications branch instead of forming one sequence. Code assessments and runnable examples declare `rust` or `cpp`; catalog validation rejects mismatches with the course language. Each node requires its own executable proof; a topic or course selection supplies no credit. Rust examples use the standard library with finite inputs, including real bounded threads and future mechanics; external async runtimes and Cargo package downloads are explained conceptually. C++ exercises use portable C++20 contracts and avoid timing claims or undefined behavior. Their [source notes](sources/cpp.md) explain the deduplicated GetCracked topic reference and original exercise scope.
