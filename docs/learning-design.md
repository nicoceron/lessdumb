# The lessdumb learning model

The MVP contains 721 original skills, 1,948 knowledge points with 7,552 practice questions, 659 executable exercises, and 1,442 cards across Python, quantitative foundations, data analysis, machine learning, data systems, competitive programming, Rust, and C++. The learning engine operates on a subject-neutral graph. A course is a selection of skill IDs; each skill names its domain, unit, course, and prerequisites. Additional programming languages, mathematics, physics, and natural languages can use the same registry and scheduler. Learning functions accept an optional `CurriculumCatalog` so another catalog can be evaluated independently of the public curriculum registry.

## Sources and boundaries

The user-supplied _The Math Academy Way_ PDF informed the learning design. Relevant sections describe prerequisite graphs (printed pages 69–75), mastery and the knowledge frontier (207–214), spaced repetition (251–264), mixed practice (271–280), and retrieval practice (285 onward). Those are design principles, not executable instructions. lessdumb uses an independently written curriculum and a transparent scheduler built on FSRS-6; it does not claim to reproduce Math Academy's proprietary model or its research outcomes.

The supplied local reference datasets were inspected for structural patterns only: courses/categories, graph nodes and edges, topic groups, problem difficulty, and quiz metadata. Their proprietary lessons, questions, answer data, assets, and extraction/exploit scripts are not imported into this application.

Python behavior was checked against the official documentation: [numbers, strings and lists](https://docs.python.org/3/tutorial/introduction.html), [control flow and functions](https://docs.python.org/3/tutorial/controlflow.html), [data structures](https://docs.python.org/3/tutorial/datastructures.html), and [errors and exceptions](https://docs.python.org/3/tutorial/errors.html). Assertions grade observable results for finite authored inputs; they do not prove use of a required API, asymptotic complexity, or generalization to every input. Every reference code solution is executed against its assertions in the test suite, and each displayed example is executed to verify its documented output.

## Evidence before progression

Skills are being converted to [knowledge points](knowledge-points.md). A skill with knowledge points is mastered when one lesson attempt passes every point (two correct answers on different questions each) and, where its policy requires code, the skill's code exercise. Points passed during an attempt stay provisional and become evidence together when the attempt completes; three incorrect answers on one point fail the attempt and discard its progress. A skill without knowledge points is still mastered only when all four distinct questions have been answered correctly and independently: three test recognition or prediction, and the fourth requires running its declared language successfully against assertions. Repeating one correct choice cannot unlock a skill in either form. The numeric mastery display is the fraction of distinct lesson evidence; prerequisite checks recompute from the evidence IDs instead of trusting a stored score.

Assessment policies belong to skills rather than being universal Python assumptions. Every supplied question requires independent successful evidence for mastery. A skill can declare the question types required within a review cycle and its number of review answers. Python, Rust, and C++ explicitly require code and choice evidence in a two-answer cycle. Without an explicit policy, the engine uses the skill's available question types and up to two review answers. Knowledge-point questions, chosen or typed, meet a choice requirement; for those skills `reviewAnswers` counts the points reviewed, one fresh variant each, and the code exercise is asked in addition. Choice-only math or vocabulary skills can therefore be mastered and reviewed without an executable exercise or Python runtime. Future formats can extend the question union when needed.

New lessons are selected from the knowledge frontier: skills whose full prerequisite ancestry has mastery evidence. Questions not previously attempted are served before retrying a missed question, and a learner never meets the same concrete question of a point within their last three attempts at it while another remains. 318 questions are generators that ask fresh numbers each time (87 in quantitative foundations, 70 in Competitive Programming, 27 in Python foundations, 51 each in Rust and C++, 32 in Python for Data Analysis), so retries, reviews, and quizzes cannot be answered from memory; each attempt stores the small variant number it asked ([generated questions](knowledge-points.md#generated-questions)). After a failed knowledge-point attempt the scheduler offers other available work first; the lesson returns after the learner completes another task or four hours later, whichever comes first, and restarts at its first point. A failure can first bring the reviews of weak prerequisites forward; the lesson then waits for them ([remediation after a failed lesson](#remediation-after-a-failed-lesson)). A learner can inspect the graph, but learning submissions for locked skills are rejected. Viewing a lesson earns no XP.

The lesson page follows the scaffolded sequence described in Math Academy's public learning process and the supplied PDF (pages 74–75, 219, and 397): one page that grows downward, like a Math Academy lesson. The page shows the lesson title, a compact bar with one progress marker per knowledge point (plus the code step) that stays in view while scrolling, and the skill's introduction. Each knowledge point the learner reaches adds a section with its explanation, a worked example, and its questions; the first question is already on the page when the lesson opens. A question has lettered choices, or a field for a typed answer, and Submit; feedback with the explanation appears under it, and Continue adds the next question below, or the next point's section once the point passes. Nothing is removed or folded away: answered questions keep their result, so the learner can scroll back to the explanation and example while solving. The code exercise comes last on the same page, and a completed or failed lesson ends with its result at the bottom. Opening a lesson records nothing; the first answer starts the attempt. Choices are shown in a deterministic shuffled order per presentation and graded against the authored answer index. Each graph skill remains an independently assessed atom; a topic's four stages retain their own graph identities. There are no hints: the worked example is the support. Reviews stack their questions on one page without lesson material; once a review question is answered, it offers its point's explanation and example to reread, collapsed by default, so recall still comes first. Older saved answers flagged as assisted are still read and still never count as evidence.

## Typed answers

With four choices a guess is right a quarter of the time, and two correct answers pass a point, so lucky guesses would count heavily. Most questions are therefore typed, as in Math Academy: 4,215 of the 7,552 knowledge-point questions (56%). A `numeric` question takes a number (an integer, a decimal, a simple fraction like `3/4`, or scientific notation like `1e-3`) and is correct within an absolute tolerance; a `text` question takes a short exact answer, usually what a program prints, compared line by line after trimming and collapsing spaces, case included. A response that is not a number gets a gentle message and is not counted at all, so a typo in the format is never a miss. Output and value questions stay multiple choice only where typing would be ambiguous: long or non-ASCII output, long decimal tails, spacing that matters, or more than one right value. [Authoring rules](knowledge-points.md#typed-answers) list the cases.

Typed questions are evidence exactly as choices are: the same two-correct and three-miss rules, the same review cycles and XP, and they satisfy a `choice` requirement. Choice shuffling does not apply to them. Quizzes and placement ask them too; placement treats a correct typed answer as stronger evidence, with a fixed guess rate of 10% (`TYPED_GUESS`) instead of one over the number of choices. The attempt, the quiz question, and the placement answer keep what the learner typed, so an answered question shows it next to the accepted answer.

A wrong answer removes evidence only for that question. Descendants are unavailable until the missing evidence is restored. Other prerequisite evidence is preserved: a mistake in a difficult skill is not proof that every ancestor is weak. If an ancestor separately loses its own evidence, the frontier naturally selects that ancestor first. This is targeted remediation based on observed evidence. A failed lesson goes further: it looks for weak prerequisites to refresh (below).

## Retrieval and spacing

Initial mastery schedules the first review one day later. A code-bearing review cycle requires two distinct unassisted correct answers, including an executable code question; other subjects follow their declared assessment policy. Only a due review can strengthen the schedule. Completed independent cycles use the maintained `ts-fsrs` implementation of FSRS-6 to update that learner/skill’s stability, difficulty, lapse count, and review date. The target retention is 90%, with deterministic scheduling and a 365-day maximum. A completed cycle containing an answer flagged as assisted (only older clients produced these) is graded Hard; otherwise it is Good. Assisted answers alone never complete a cycle or move its due date. A failure records Again, lowers memory strength, and clears the failed question’s evidence. Repair keeps that reduced memory state and sets a conservative one-day check. Default FSRS weights are shared; parameters are not trained per learner. Early practice does not move the due date or earn review XP. A failed question restores the skill to learning/remediation and starts a one-day review interval after its evidence is repaired.

Due reviews come before new learning, but never more than two in a row while a lesson is ready (`MAX_CONSECUTIVE_REVIEWS`): after two finished review tasks since the learner's last lesson answer, the next task is a lesson, and then reviews resume. A review task is finished when its cycle passes or a missed answer ends it. When no lesson is ready, reviews simply continue, and `/learn?mode=review` stays a review-only session. The Learn task list follows the same rule. When several skills are due, adaptive sessions interleave after each answer so the last practiced skill is not repeatedly selected. Directly opening a specific skill keeps a focused session. Within the course-priority group, due candidates with lower estimated recall come first. A due descendant whose prerequisite needs remediation waits until that prerequisite is restored. The scheduler makes no claim that success in an advanced skill demonstrates retention of every ancestor; implicit credit (below) reaches direct prerequisites only.

## Implicit review credit

Every prerequisite edge means the dependent skill's lesson or questions actually use that skill ([graph rules](knowledge-graph.md)), so succeeding at a skill also exercises its direct prerequisites, in the spirit of Math Academy's FIRe. Each skill encompasses its direct prerequisites with a weight in (0, 1]: `encompasses` on the skill when authored, otherwise every direct prerequisite at 0.25 (`DEFAULT_ENCOMPASS_WEIGHT`). The weights are authored heuristics, not parameters fitted to learners, and the default is deliberately low.

When a learner completes a lesson or a review cycle of a skill, or answers it correctly in a quiz, each encompassed prerequisite that is mastered, unlocked, scheduled, and not part-way through its own review cycle gets implicit credit. Its due date moves later by the weight times the interval a full successful review at that moment would add (FSRS Good from its current memory), so it can never move past what a real review would schedule. Credit is given at most once per prerequisite per calendar day, and never on the day the prerequisite was itself learned or reviewed, so a new skill keeps its first one-day check. Credit stops at direct prerequisites; nothing trickles further up the graph. It changes only the due date: FSRS stability, difficulty, repetitions, and estimated recall change only through real reviews, so a later real review sees the full elapsed time. Failures give no credit and change nothing upstream. A lapsed or remediating skill is not mastered and gets nothing, and credit never creates mastery. A quiz miss, a real review, or a lapse after a credit takes precedence over it.

The credit is recorded on the prerequisite (`implicitCredit`: source skill, weight, time, and the due date before and after) and on the answer that gave it (`credited`), so merges keep a credit that a stale device lacks, and the history feed can note "+ reviewed N prerequisites". The graph's detail panel lists which skills also review a skill and notes when practice moved its next review.

Review compression: among due reviews, after course priority and the rule that keeps the most recently practiced skill from repeating, the scheduler prefers a review whose success would credit more skills that are due or due within a day. The interleaving with lessons is unchanged.

## Placement diagnostic

An optional placement test (`src/lib/placement.ts`) lets a learner skip lessons they can already do. Courses offers it for the active course, and Learn offers it to a learner who has not answered anything yet; skipping starts from the beginning as before. The test covers the selected course's whole prerequisite path, supporting courses included, and asks knowledge-point choice and typed questions only, with no code editor. It shows a progress indicator but never whether an answer was right, and an interrupted test resumes on the same question.

It is a transparent heuristic, not Math Academy's calibrated model. Every path skill has a probability that the learner already knows it, starting at even odds (certain for skills with real mastery evidence). An answer updates the tested skill by Bayes' rule with a fixed 10% slip rate and a guess rate of one over the number of choices, or 10% for a typed answer. Because an edge means "uses", a correct answer also raises every ancestor and a wrong answer lowers every descendant, with the evidence shrinking by a factor of 0.85 per hop. A correct answer that took longer than a minute, measured by the page from showing the question to submitting it, counts as half the evidence. A skill at 85% or more is classified as known, and at 15% or less as not known. The next question goes to the uncertain skill whose answer is expected to settle the most uncertain skills, weighing a right and a wrong answer by their predicted chance, with ties going to the skill that splits the uncertain region most evenly; a skill is asked at most twice and a question never repeats. The test stops when every skill is classified, nothing uncertain can be asked, or after 48 questions. The slip rate, hop factor, thresholds, and time cutoff are authored values that have not been fitted to learners.

Placement is conservative. Only skills classified as known whose every prerequisite is mastered or placed are placed, and never a skill the learner has already answered or opened: real evidence always wins. A placed skill counts as mastered for unlocking and earns no XP and no cards. Its first review is due within one to 14 days, with the most advanced placed skills first and at most about eight a day. Passing that review confirms the placement; a wrong answer before then removes the placement's evidence for the whole lesson, records a lapse, and returns the skill to learning from its first point. Placed skills take no implicit review credit until their first review. A test can be retaken; retaking only adds placements and never removes mastery. The report shows the skills placed out of, where learning starts (the frontier), unmastered foundations from supporting courses, and an estimated finish from the daily goal.

## Remediation after a failed lesson

A learner stuck on a skill is often missing something underneath it, so Math Academy reviews a struggling learner's weak prerequisites first. When a knowledge-point lesson attempt fails (three misses on one point), `src/lib/remediation.ts` scores each direct prerequisite for weakness as a sum of signals:

| Signal       |          Weight | Meaning                                                                                                          |
| ------------ | --------------: | ---------------------------------------------------------------------------------------------------------------- |
| `placement`  |               3 | Placed out by the diagnostic, and its first review has not confirmed it yet.                                     |
| `unobserved` |               3 | Mastered, but this learner has never answered it at all.                                                         |
| `due`        |               2 | Its review is due or overdue.                                                                                    |
| `mistakes`   | 1 each, up to 3 | Wrong answers on it, in any mode and question type, in the last 14 days.                                         |
| `unstable`   |               1 | FSRS stability below 7 days: learned recently or barely reviewed.                                                |
| `lapsed`     |               1 | Forgotten before (FSRS lapses) and still unstable.                                                               |
| `implicit`   |               1 | Its review would be due by now, but implicit credit postponed it, so no real review backs its schedule (CEN-88). |

A first failure refreshes only clearly weak prerequisites, with a score of 2 or more. After two or more failures in a row, any signal counts; the streak is counted from the attempt log, back to the lesson's last pass. The weakest one or two above the threshold are refreshed: highest score first, then lower estimated recall, then lower stability. Only when every direct prerequisite is below the threshold does the engine look one layer down, at the prerequisites of the prerequisites, by the same rule; it never goes further. Solid prerequisites trigger nothing, and the lesson keeps its usual cooldown. A prerequisite whose recall was checked after the previous failure of the same lesson (a real review or a correct answer, with no mistake since) counts as solid for this failure. Repeated failures therefore move on, usually one layer down, instead of refreshing the same skill again.

A refresh is an ordinary review brought forward. The prerequisite's due date becomes the failure time; its FSRS memory is kept, so the review is scheduled from the real elapsed time; any implicit credit on it is dropped. The only stored state is `refresh` on the prerequisite: the failed lesson and the failure time, about 60 bytes, kept only while the review is pending. Everything else is derived: the streak from the attempt log, the refreshed list from these markers, and whether a refresh is done from the FSRS memory's last review, which a real review moves past the failure time. Saved state has a 4 MiB cap, so nothing more is stored. Refreshes go through the existing machinery: due refreshes come first among due reviews in `nextTask` and on Learn, still at most two reviews in a row while a lesson is ready, and they pay review XP. A pending refresh takes no implicit credit. The failed lesson waits until its refreshes are done, for at most a day (`REFRESH_HOLD_MS`); after that the usual cooldown rule applies. A passed or failed review settles a refresh; a failed one lapses the prerequisite like any review, so it is relearned before the lesson unlocks again. The learner is told why in plain words: "Before trying X again, let's refresh Y." The sentence appears on the failed-lesson message at the bottom of the lesson page, with a button that starts the review, on the review's Learn task card, and above the review's questions. Merges keep a refresh that a stale device lacks until a real review; a credit recorded later by a device that had not seen the refresh wins.

The signals, weights, and thresholds are authored heuristics, not values fitted to learners.

## Quizzes

After about 150 XP of lessons and reviews since the previous quiz (`QUIZ_XP_INTERVAL`, quiz XP excluded), a quiz appears on Learn as a task card ("Quiz N" with its XP). It plans ten multiple-choice or typed questions, one from each of the ten highest-priority skills the learner has mastered on the active course path, supporting skills from other courses included. A skill's priority is its weakness plus its staleness. Weakness, from 0 to 1, rises with low FSRS stability (half at 7 days of stability) and halves the remaining strength with each wrong answer on the skill in the last 14 days, in any mode. Staleness rises from 0 just after the skill was quizzed to 1 after 14 days, and is 1 for a skill never quizzed. The active course's own skills get a 0.2 bonus; ties go to the most recently practiced, then teaching order. Each question is a variant from the skill's knowledge point with the most recent mistakes, otherwise its least-practiced point, and is the variant the learner has seen least, unseen first. When fewer than eight skills qualify, skills contribute a second question from another point; with fewer than four no quiz is offered.

The length adapts to the answers (`quizContinues`), between 8 and 14 questions. When the first eight answers are all right, the learner is clearly solid and the quiz ends there; the planned questions not reached are dropped. Otherwise it reaches its planned ten, and continues from there while results are mixed: under 85% correct and at least 50%. At 85% or more it ends, and under half right it ends too, since every miss already schedules a review. Each added question comes from the highest-priority skill not yet asked, with the prerequisites of skills missed in this quiz boosted by 0.5, so a growing quiz probes beneath its misses; when every skill is in, it asks another point of a skill answered correctly. The time limit is 90 seconds per question, shown as a countdown, and each added question adds its 90 seconds. During the quiz there is no lesson material, no feedback, and no explanation; at the end the learner sees the score, the XP, and every question's result with its explanation. Unanswered questions at the time limit count as missed.

A missed question makes its skill's review due immediately and starts a fresh review cycle; it does not remove lesson evidence or record an FSRS lapse by itself, so the remedial review decides, and failing it records Again as any review does. A correct quiz answer on a skill whose review is already due counts toward that cycle, but only a review answer can complete a cycle, so a quiz never moves a due date forward. A correct answer on any other skill changes no schedule, just as early practice does. These are deliberately conservative choices: FSRS memory changes only through review tasks. Selection and length adapt to the learner; question difficulty is not adapted toward a target score, since doing that honestly would need calibrated per-question difficulty, which the catalog does not have. The priority weights and accuracy thresholds are authored heuristics.

## Progress, XP, and cards

Progress updates are immutable and have an explicit schema version. Version 7 adds the variant number of a generated question to attempts, quiz questions, and placement questions (`variant`; older entries without one name the authored question); version 6 adds the pending refresh a failed lesson schedules on a prerequisite (`refresh`); version 5 adds placement diagnostics (the latest 10) and per-skill placements; version 4 adds implicit review credit; version 3 adds saved quizzes (the latest 50, each with its questions, answers, score, and XP) and quiz answers in the attempt log; version 2 adds the lesson attempt in progress, the last failed attempt time, and a one-time lesson reward flag per skill; version 1 accounts migrate when they are read, and mastery earned under the four-question lesson is kept when a skill gains knowledge points. Only the latest 2,000 events are retained for diagnostics, while durable per-question evidence checkpoints, permanent reward IDs, per-skill XP/calendar totals, and answer counters survive compaction. Per-runtime writer counters merge by component maxima, so a late offline observation is counted even when its timestamp predates another device’s newest work. Writer contributions are retained rather than silently evicted. Merges reconcile different evidence from the same review cycle once, preserve newer retention events across newer lesson reads, and do not resurrect a compacted failure from a stale device. Simultaneous conflicting retention outcomes choose a deterministic conservative memory state, so device merge order does not decide the review date. Stable attempt IDs deduplicate retries within the retained event window. Attempt history records question ID, skill ID, answer outcome, the legacy assisted flag, practice mode, timestamp, awarded XP, and, on the answer that completed or failed a task, its task outcome. Epoch milliseconds represent scheduling times; ISO strings represent attempt timestamps and the first mastery timestamp. Calendar dates and streaks use the learner's recorded IANA timezone.

XP is paid per completed task (`src/lib/xp.ts`), on the answer that completes it, at about one XP per focused minute: a lesson is worth three XP per knowledge point plus two (or its estimated minutes for a skill without knowledge points), with a quarter bonus for a perfect task and one XP less per incorrect answer, never below one. A lesson pays once per skill: a one-time reward flag, plus the older per-question reward ledger netted against the award, prevents relearning, remediation, or deliberate failure from farming it. Failed attempts earn nothing. A quiz is worth 1.5 XP per question asked, rounded (12 XP for eight questions, 15 for ten, 21 for fourteen), scaled by accuracy and rounded: nine of ten correct earns 14 of 15 XP. Quiz XP is recorded on the quiz itself, so merges count each quiz once. A due review cycle earns its review XP once; merges credit a lesson or cycle completed on two devices once. XP measures completed practice in this application; it does not certify programming proficiency.

Flashcards contain one idea each and are associated with stable skill/card IDs. Mastered skills earn their two cards for automated Anki export/sync. The full registry remains available for explicit curriculum previews. Each card is original, and deterministic IDs let the integration update existing notes instead of creating duplicates.

## Verification and limitations

Tests cover graph references and cycles, mastery evidence, knowledge-point passing and failure, retry cooldown, shuffled-choice grading, typed-answer parsing, normalization, and tolerance edges, legacy assisted answers, schema migration, prerequisite gates, remediation signals and refreshes after failed lessons, adaptive quiz selection and length, question rotation, review timing, distinct executable review evidence, XP replay resistance, immutable updates, timezone/streak boundaries, and reachability of each course and its full prerequisite path. Real Pyodide executes all 297 solutions and 304 executable lesson examples with the locally served scientific packages. The original Python course also retains native execution and choice-output verification. Native Rust and C++ batches verify all 361 solutions and 361 runnable examples, and reject each unfinished starter and empty submission. Real browser runs separately verify Compiler Explorer grading, account persistence, automatic cards, prerequisite unlocks, and a due code-plus-choice FSRS review in each language. Provider outages preserve evidence. Python stays in a browser worker; compiled source is transmitted without account data through the documented sandbox adapter. See [runtime boundaries](compiled-code.md). Test-only math and vocabulary catalogs verify cross-course prerequisites, choice-only mastery/review, and a custom one-answer review policy. The production catalog includes original cross-course math, data, ML, systems, and contest nodes. Competitive Programming reuses the real Python function path and connects geometry to quantitative vectors; it has no separate or implicit unlock store.

FSRS supplies a published memory model and per-item adaptation, but these estimates have not been validated or individually fitted on lessdumb learners. The one-day acquisition/repair check is a conservative product rule. Legacy schedules migrate on the next memory event without moving existing due dates. Authored questions (four per legacy skill, three or more per knowledge point) provide finite evidence; generated questions add fresh numbers for 184 points, but not new kinds of question, and the other points keep a finite bank. The MVP has no credit transfer beyond implicit review credit along direct prerequisite edges. Placement is a heuristic diagnostic, not a calibrated one, and remediation and quiz priorities are authored heuristics. The generic graph and versioned progress contract leave room for those features without replacing the learning record.

## Atomic contest topics

Competitive Programming has 48 original application skills plus 144 prerequisite concepts. Each topic’s four skills have stable topic/stage metadata, a short lesson, runnable example, three conceptual checks, one executable assessment, and two recall cards. Prerequisites, not stage numbers, govern eligibility: a concept that does not use its sibling is available alongside it, and the application requires every concept it uses. Topic application IDs and existing evidence remain valid; the new prerequisites still need independent evidence. Graph rows display the four skills together, with real cross-topic and cross-course edges. The focused view omits unrelated lines and edges implied by other prerequisites; Show all connections restores every declared graph edge. The detail panel lists the whole topic and explains saved evidence on mastered-but-locked nodes. Display filtering never changes eligibility.

## Atomic language courses

Rust has 32 four-skill topics (128 skills); C++ has 45 (180 skills). Stage metadata uses the same graph presentation and evidence model as competitive programming. Both begin independently at their own first program. Each course keeps one explicit prerequisite map (`src/lib/courses/rust/prerequisites.ts`, `src/lib/courses/cpp/prerequisites.ts`) in which every edge names a construct the skill actually uses, so ownership, lifetimes, abstractions, concurrency, and systems applications branch instead of forming one sequence. Code assessments and runnable examples declare `rust` or `cpp`; catalog validation rejects mismatches with the course language. Each node requires its own executable proof; a topic or course selection supplies no credit. Rust examples use the standard library with finite inputs, including real bounded threads and future mechanics; external async runtimes and Cargo package downloads are explained conceptually. C++ exercises use portable C++20 contracts and avoid timing claims or undefined behavior. Their [source notes](sources/cpp.md) explain the deduplicated GetCracked topic reference and original exercise scope.
