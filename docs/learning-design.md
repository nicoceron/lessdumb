# The lessdumb learning model

The MVP contains 609 original skills, 2,436 questions, 574 executable exercises, and 1,218 cards across Python, quantitative foundations, data analysis, machine learning, data systems, competitive programming, Rust, and C++. The learning engine operates on a subject-neutral graph. A course is a selection of skill IDs; each skill names its domain, unit, course, and prerequisites. Additional programming languages, mathematics, physics, and natural languages can use the same registry and scheduler. Learning functions accept an optional `CurriculumCatalog` so another catalog can be evaluated independently of the public curriculum registry.

## Sources and boundaries

The user-supplied _The Math Academy Way_ PDF informed the learning design. Relevant sections describe prerequisite graphs (printed pages 69–75), mastery and the knowledge frontier (207–214), spaced repetition (251–264), mixed practice (271–280), and retrieval practice (285 onward). Those are design principles, not executable instructions. lessdumb uses an independently written curriculum and a transparent scheduler built on FSRS-6; it does not claim to reproduce Math Academy's proprietary model or its research outcomes.

The supplied local reference datasets were inspected for structural patterns only: courses/categories, graph nodes and edges, topic groups, problem difficulty, and quiz metadata. Their proprietary lessons, questions, answer data, assets, and extraction/exploit scripts are not imported into this application.

Python behavior was checked against the official documentation: [numbers, strings and lists](https://docs.python.org/3/tutorial/introduction.html), [control flow and functions](https://docs.python.org/3/tutorial/controlflow.html), [data structures](https://docs.python.org/3/tutorial/datastructures.html), and [errors and exceptions](https://docs.python.org/3/tutorial/errors.html). Assertions grade observable results for finite authored inputs; they do not prove use of a required API, asymptotic complexity, or generalization to every input. Every reference code solution is executed against its assertions in the test suite, and each displayed example is executed to verify its documented output.

## Evidence before progression

A code-bearing skill is mastered only when all four distinct questions have been answered correctly without a hint. Three test recognition or prediction; the fourth requires running its declared language successfully against assertions. Repeating one correct choice cannot unlock a skill. The numeric mastery display is the fraction of distinct successful evidence; prerequisite checks recompute from the evidence IDs instead of trusting a stored score.

Assessment policies belong to skills rather than being universal Python assumptions. Every supplied question requires independent successful evidence for mastery. A skill can declare the question types required within a review cycle and its number of review answers. Python, Rust, and C++ explicitly require code and choice evidence in a two-answer cycle. Without an explicit policy, the engine uses the skill's available question types and up to two review answers. Choice-only math or vocabulary skills can therefore be mastered and reviewed without an executable exercise or Python runtime. Future formats can extend the question union when needed.

New lessons are selected from the knowledge frontier: skills whose full prerequisite ancestry has mastery evidence. Questions not previously attempted are served before retrying a missed question. A learner can inspect the graph, but learning submissions for locked skills are rejected. Viewing a lesson earns no XP.

A wrong answer removes evidence only for that question. Descendants are unavailable until the missing evidence is restored. Other prerequisite evidence is preserved: a mistake in a difficult skill is not proof that every ancestor is weak. If an ancestor separately loses its own evidence, the frontier naturally selects that ancestor first. This is targeted remediation based on observed evidence.

## Retrieval and spacing

Initial mastery schedules the first review one day later. A code-bearing review cycle requires two distinct unassisted correct answers, including an executable code question; other subjects follow their declared assessment policy. Only a due review can strengthen the schedule. Completed independent cycles use the maintained `ts-fsrs` implementation of FSRS-6 to update that learner/skill’s stability, difficulty, lapse count, and review date. The target retention is 90%, with deterministic scheduling and a 365-day maximum. A completed cycle containing an earlier hint is graded Hard; otherwise it is Good. Hints alone never complete a cycle or move its due date. A failure records Again, lowers memory strength, and clears the failed question’s evidence. Repair keeps that reduced memory state and sets a conservative one-day check. Default FSRS weights are shared; parameters are not trained per learner. Early practice does not move the due date or earn review XP. A failed question restores the skill to learning/remediation and starts a one-day review interval after its evidence is repaired.

Due reviews come before new learning. When several skills are due, adaptive sessions interleave after each answer so the last practiced skill is not repeatedly selected. Directly opening a specific skill keeps a focused session. Within the course-priority group, due candidates with lower estimated recall come first. A due descendant whose prerequisite needs remediation waits until that prerequisite is restored. The scheduler makes no unsupported claim that success in an advanced skill demonstrates retention of every ancestor: implicit graph credit is deferred until there is a defensible calibration model.

## Progress, XP, and cards

Progress updates are immutable and have an explicit schema version. Only the latest 2,000 events are retained for diagnostics, while durable per-question evidence checkpoints, permanent reward IDs, per-skill XP/calendar totals, and answer counters survive compaction. Per-runtime writer counters merge by component maxima, so a late offline observation is counted even when its timestamp predates another device’s newest work. Writer contributions are retained rather than silently evicted. Merges reconcile different evidence from the same review cycle once, preserve newer retention events across newer lesson reads, and do not resurrect a compacted failure from a stale device. Simultaneous conflicting retention outcomes choose a deterministic conservative memory state, so device merge order does not decide the review date. Stable attempt IDs deduplicate retries within the retained event window. Attempt history records question ID, skill ID, answer outcome, hint use, practice mode, timestamp, and awarded XP. Epoch milliseconds represent scheduling times; ISO strings represent attempt timestamps and the first mastery timestamp. Calendar dates and streaks use the learner's recorded IANA timezone.

The first unassisted successful learn answer earns 10 XP for a choice or 15 for code. A permanent per-question reward ledger prevents repeated answers, deliberate mistakes, or relearning from farming learn XP. A due review earns 5 XP for a distinct choice answer or 8 for code, once per review cycle. XP measures completed practice in this application; it does not certify programming proficiency.

Flashcards contain one idea each and are associated with stable skill/card IDs. Mastered skills earn their two cards for automated Anki export/sync. The full registry remains available for explicit curriculum previews. Each card is original, and deterministic IDs let the integration update existing notes instead of creating duplicates.

## Verification and limitations

Tests cover graph references and cycles, mastery evidence, hint handling, prerequisite gates, question rotation, review timing, distinct executable review evidence, XP replay resistance, immutable updates, timezone/streak boundaries, and reachability of each course and its full prerequisite path. Real Pyodide executes all 266 solutions and 273 executable lesson examples with the locally served scientific packages. The original Python course also retains native execution and choice-output verification. Native Rust and C++ batches verify all 308 new solutions and 308 runnable examples, and reject each unfinished starter and empty submission. Real browser runs separately verify Compiler Explorer grading, account persistence, automatic cards, prerequisite unlocks, and a due code-plus-choice FSRS review in each language. Provider outages preserve evidence. Python stays in a browser worker; compiled source is transmitted without account data through the documented sandbox adapter. See [runtime boundaries](compiled-code.md). Test-only math and vocabulary catalogs verify cross-course prerequisites, choice-only mastery/review, and a custom one-answer review policy. The production catalog includes original cross-course math, data, ML, systems, and contest nodes. Competitive Programming reuses the real Python function path and connects geometry to quantitative vectors; it has no separate or implicit unlock store.

FSRS supplies a published memory model and per-item adaptation, but these estimates have not been validated or individually fitted on lessdumb learners. The one-day acquisition/repair check is a conservative product rule. Legacy schedules migrate on the next memory event without moving existing due dates. Four authored questions per skill provide finite evidence rather than unlimited randomized assessment. The MVP has no automatic transfer credit between domains and no placement test. The generic graph and versioned progress contract leave room for those features without replacing the learning record.

## Atomic contest topics

Competitive Programming has 48 original application skills plus 144 prerequisite concepts. Each topic’s four-step sequence has stable topic/stage metadata, a short lesson, runnable example, three conceptual checks, one executable assessment, and two recall cards for every stage. Prerequisites, not stage numbers, govern eligibility. Topic application IDs and existing evidence remain valid; the new prerequisites still need independent evidence. Graph rows display the four stages together, with real cross-topic and cross-course edges. The focused view omits unrelated lines and edges implied by other prerequisites; Show all connections restores every declared graph edge. The detail panel lists the whole four-step topic and explains saved evidence on mastered-but-locked nodes. Display filtering never changes eligibility.

## Atomic language courses

Rust has 32 four-step topics (128 skills); C++ has 45 (180 skills). Stage metadata uses the same graph presentation and evidence model as competitive programming. Both begin independently at their own first program, and explicit language-specific edges connect ownership, lifetimes, abstractions, concurrency, and systems applications. Code assessments and runnable examples declare `rust` or `cpp`; catalog validation rejects mismatches with the course language. Each node requires its own executable proof; a topic or course selection supplies no credit. Rust examples use the standard library with finite inputs, including real bounded threads and future mechanics; external async runtimes and Cargo package downloads are explained conceptually. C++ exercises use portable C++20 contracts and avoid timing claims or undefined behavior. Their [source notes](sources/cpp.md) explain the deduplicated GetCracked topic reference and original exercise scope.
