# Learning engine audit

Audited against the user-supplied _The Math Academy Way_ working-draft PDF and [lessdumb's learning design](learning-design.md), on October 2, 2026. Page references below are the book's printed pages. The document is reference material; its descriptions of Math Academy are not instructions to this application.

**The MVP's adaptive learning loop is implemented and tested. The complete engine described in the book is not.** lessdumb makes recommendations from each learner's evidence, mistakes, hints, activity, review dates, and course goal. Its graph and review rules are working product behavior, but they are a simpler model than Math Academy's diagnostics, retention calibration, and hierarchical reinforcement.

The current catalog has 157 original skills and four authored questions per skill, across Python, quantitative foundations, data analysis, machine learning, data systems, and competitive programming. Original content and transparent rules do not establish equivalence to Math Academy's proprietary implementation or reported educational outcomes. Account and browser ownership checks are documented separately in [the account isolation audit](account-isolation.md).

## Concrete corrections made during this audit

### A lapse now blocks the full dependent path

Previously, eligibility checked only direct parents. In `printing → variables → numbers`, a failed printing question left variables' earlier evidence intact, so numbers still appeared eligible through that parent. Eligibility now traverses the full prerequisite ancestry. A learner must repair printing before using numbers again. Variables and numbers retain their own evidence, and become available again after the missing foundation is repaired. The traversal also fails safely for unknown nodes and cycles.

### Review recovery now uses current spacing strength

Previously, the next interval was selected from lifetime `reviewCount`. A learner could fail a topic, relearn it with a one-day review date, and then jump straight to a 60- or 120-day interval because of earlier successful reviews. The next successful review now advances from the current `intervalDays`. Recovery proceeds from one to three days, while `reviewCount` continues to record the lifetime number of completed cycles.

This change does not introduce a fitted forgetting model. It makes the existing restart rule internally consistent.

## Verification

Run the relevant suite with:

```sh
npx vitest run tests/learning.test.ts tests/catalog.test.ts
```

At this audit, both files passed: **30 tests**. The coverage includes graph validation, every course's reachable prerequisite path, locked submissions, mastery and hints, question rotation, due-only review credit, required review types, immutable updates, reward replay resistance, timezone/streak boundaries, and the original Python course's executable reference solutions and output predictions.

The new tests compare divergent learner histories rather than merely checking a shared sequence:

- With the same previously mastered three-skill path, a learner who loses ancestor evidence receives repair work and cannot submit dependent work. A learner who successfully retrieves that ancestor receives a different due task. Repair restores eligibility without erasing descendant evidence or granting repeated learn XP.
- With the same four correct answers and 100% answer accuracy, independent and hinted learners receive different mastery, review dates, and next tasks.
- Two learners with five lifetime successful review cycles receive different spacing after different retention outcomes: the retained path advances to 60 days; the recovered path advances to three days after its lapse and repair.

These tests establish the engine's deterministic rules for the provided scenarios. They do not independently establish browser grading, account persistence, Anki delivery, deployment, or educational effectiveness; those need their own integration checks. See [account isolation evidence](account-isolation.md) for per-account ownership and persistence verification.

## What remains before a complete book-level engine

A defensible implementation would still need an adaptive placement workflow, sufficiently varied assessments, question/knowledge-point links for prerequisite diagnosis, calibrated student-topic retention, and separately authored encompassing relationships before any implicit reinforcement or review compression. Those capabilities are missing, not hidden behind the current UI.

Until then, the accurate claim is: **lessdumb has a functioning, per-learner prerequisite/mastery/review MVP with fixed spacing and targeted evidence repair. It does not yet implement every engine capability described in _The Math Academy Way_.**
